# Lean PRD: 카테고리 관리

- 상태: 계획 / 미착수
- 구현 브랜치: `feature/category-management`
- 선행 기준: [전체 PRD](PRD.md), [공통 CLI 보완](PRD-002.md), [거래 CRUD](PRD-001.md)

## 1. 목적

등록 카테고리를 별도 명령으로 관리하고, 거래가 존재하지 않는 카테고리를 참조하지 않도록 한다.
PRD-001의 저장 구조와 거래 추가 중 카테고리 등록 흐름을 재사용한다.

## 2. 범위

### 포함

- `category add/list/remove` 및 각 명령의 도움말
- 대화형 카테고리 추가·삭제, 저장 순서의 목록 조회
- 빈 이름·중복 이름·존재하지 않는 이름 검증
- 사용 중 카테고리 삭제 거부
- 초기 빈 목록 안내, 거래 수정 시 등록 카테고리 검증

### 제외

- 카테고리 이름 변경, 대체 카테고리 지정, 거래 일괄 이동
- 기본 카테고리 자동 생성, 수입·지출별 카테고리 분리

## 3. 사용자 시나리오

옵션 접두사는 [전체 PRD의 CLI 표기](PRD.md#5-cli-표기)를 따른다.

```zsh
python -m budget_app category add
python -m budget_app category list
python -m budget_app category remove
python -m budget_app category -help
```

`add`와 `remove`는 카테고리 이름을 대화형으로 입력받는다.
등록·삭제 성공 시 결과와 이름을 출력한다. `list`는 한 줄에 이름 하나를 저장 순서대로 출력한다.
목록이 비어 있으면 “등록된 카테고리 없음”과 `category add` 실행 안내를 출력한다.

카테고리가 하나도 없는 상태에서 거래 `add`를 실행하면 등록 안내 후 오류 종료한다.
카테고리가 이미 하나 이상 있으면 PRD-001의 미등록 이름 등록·재입력 흐름을 유지한다.
이 초기 빈 목록 정책은 PRD-001의 거래 추가 흐름을 보완한다.

## 4. 데이터 모델

기존 카테고리 모델을 유지한다. 이름은 앞뒤 공백을 제거한 비어 있지 않은 문자열이다.
대소문자는 구분하므로 `food`와 `Food`는 다른 이름이다.
같은 이름은 한 번만 등록할 수 있으며, 거래의 `category`는 등록 이름과 일치해야 한다.

```json
{"name":"food"}
{"name":"salary"}
```

## 5. 저장 방식

- 공통 데이터 폴더의 `categories.jsonl`에 UTF-8 JSONL로 저장한다.
- 추가는 기존 저장 순서의 끝에 반영한다. 조회는 기존 제너레이터를 사용한다.
- 삭제는 먼저 `transactions.jsonl`을 순회해 해당 이름의 사용 여부를 확인한다.
- 사용 중이면 수입·지출 구분 없이 삭제를 거부하고 두 파일을 변경하지 않는다.
- 삭제 가능하면 같은 폴더의 임시 파일에 나머지 행을 기록한 뒤 원자적으로 교체한다.
- 교체 전 실패하면 원본을 유지하고 임시 파일을 정리한다.

## 6. 구조

- `cli.py`: 관리 명령 연결, 대화형 입력, 성공·빈 목록 출력
- `validators.py`: 기존 카테고리 이름 검증 재사용
- `services.py`: 중복 등록·사용 중 삭제 검증과 거래 추가·수정의 참조 검증
- `repositories.py`: 기존 `CategoryRepository`의 조회·추가 재사용 및 삭제 구현

기존 구조를 확장하며 별도 계층이나 이름 변경 기능을 추가하지 않는다.
공통 오류 출력·종료 코드는 PRD-002를 따른다.

## 7. 주요 검증 규칙

- 공백뿐인 이름은 오류로 처리한다.
- 명시적 `category add`의 중복 등록은 오류이며 기존 행을 중복 저장하지 않는다.
- 없는 이름의 삭제는 오류이며 파일을 변경하지 않는다.
- 사용 중인 이름 삭제 오류에는 연결된 거래를 먼저 수정·삭제하라는 힌트를 제공한다.
- 거래 `update -id TX-000001 -category food`는 등록 여부를 검증한다.
- 거래 수정에서 미등록 이름은 자동 등록하지 않고 오류로 처리하며 기존 거래를 유지한다.

## 8. 완료 조건

표준 라이브러리 `unittest`로 다음 수용 사례를 검증한다.

| 사례 | 기대 결과 |
| --- | --- |
| ` food ` 추가 후 재실행 | `food` 한 행이 유지되고 목록에 표시 |
| `food` 중복 추가 / 공백 이름 추가 | 오류 종료, 저장 내용 유지 |
| `food`, `Food` 등록 | 두 이름을 저장 순서대로 조회 |
| 미사용 이름 삭제 / 없는 이름 삭제 | 각각 성공 / 오류, 다른 이름 유지 |
| 거래가 참조하는 이름 삭제 | 오류 종료, 카테고리·거래 파일 유지 |
| 빈 목록에서 거래 추가 | `category add` 안내, 거래 저장 없음 |
| 기존 목록에서 미등록 이름으로 거래 추가 | 기존 등록·재입력 흐름 동작 |
| 거래 카테고리를 미등록 이름으로 수정 | 오류 종료, 기존 거래 내용 유지 |
| 임시 파일 기록 또는 교체 실패 | 원본 유지, 공통 오류·힌트, 임시 파일 정리 |

각 관리 명령의 도움말과 재실행 후 영구 저장을 확인한다.
관련 테스트와 전체 테스트, Ruff 포맷·검사를 통과하고 README·PROGRESS를 갱신한다.

## 9. 구현 순서

1. 이름·중복·사용 여부 정책을 서비스에 연결한다.
2. 저장소 삭제와 관리 CLI를 구현한다.
3. 초기 거래 추가 안내와 거래 수정 검증을 보완한다.
4. 수용 사례 및 회귀 테스트를 실행하고 문서를 갱신한다.
